# SunDO.

학생 선도 기록을 다루는 학교 PWA에서, **백엔드 서버 없이 행 수준 접근 제어(RLS)만으로 권한을 강제**한 프로젝트.
클라이언트 SDK가 데이터베이스에 직접 접근하는 구조라 **보안 규칙이 유일한 방어선**이었고,
규칙을 "통과하는가"가 아니라 **"거부가 실제로 일어나는가"** 로 검증하기 위해
250개 케이스와 **44종의 규칙 변형(mutation) 역검증**을 붙였다.

---

## *Motive.*

자율생활부의 선도 기록은 종이로 관리되고 있었다.
누가 언제 무엇을 적었는지 추적할 수 없고, 잘못 적은 기록을 지우면 흔적이 남지 않으며,
어떤 학생의 기록을 누가 볼 수 있는지가 문서로 정의되어 있지 않았다.

전자화 자체는 어렵지 않다. 문제는 **다루는 데이터가 미성년자의 생활지도 기록**이라는 점이다.
잘못 설계하면 종이보다 나빠진다 — 종이는 물리적으로 한 부지만, 데이터베이스는 질의 한 줄로 전교생 기록이 나온다.

### *구조가 만든 제약*

이 앱에는 **애플리케이션 서버가 없다.** 브라우저의 클라이언트 SDK가 데이터베이스에 직접 접속한다.

```
[브라우저] ──직접──> [Firestore]
              ▲
        여기에 규칙이 없으면 아무것도 없다
```

서버가 있는 구조라면 권한 판정은 서버 코드가 하고, 클라이언트는 그 앞을 지나가기만 한다.
서버가 없으면 **권한 판정을 할 수 있는 자리가 보안 규칙 한 곳뿐**이다.
화면에서 버튼을 숨기는 것은 방어가 아니다 — 콘솔에서 SDK를 직접 호출하면 그만이다.

> 🎯 **설계 원칙**
> 화면은 **편의**를 담당하고, 규칙은 **강제**를 담당한다.
> 화면이 막는 것과 규칙이 막는 것이 다르면, 실제로 막히는 것은 규칙이 막는 것뿐이다.

## *Research Q & H.*

> 서버 없이 규칙만으로 권한을 강제할 수 있는가? 그리고 그 규칙이 실제로 작동한다는 것을 어떻게 증명하는가?

- **가설 1 (규칙 단독 강제)** — 역할·상태·필드 단위 조건을 규칙에 표현하면, 애플리케이션 서버 없이도 조직의 권한 체계를 강제할 수 있을 것이다.
- **가설 2 (통과 검증의 무효성)** — "허용되어야 할 것이 허용된다"만 검증하면 **조건을 아예 쓰지 않은 규칙도 통과한다.** 따라서 거부 케이스와 그 거부가 실제로 일어난다는 증명이 함께 필요할 것이다.
- **가설 3 (문서 단위 한계)** — 규칙은 문서 단위로 평가되므로, 집합 전체에 걸린 불변식(예: "부장은 정확히 1명")은 규칙만으로 보장할 수 없을 것이다.
- **가설 4 (좁히기의 비용)** — 권한을 좁히면 그 권한에 의존하던 화면이 죽는다. 좁히기 전에 **소비자를 세는 절차**가 없으면 배포 순간 특정 화면이 무동작이 될 것이다.
- **가설 5 (문서와 실측의 괴리)** — 명세 문서가 규정한 조건과 실제 엔진의 동작은 어긋날 수 있으며, 실측 없이 문서만 따르면 정상 사용자가 거부되거나 공격이 통과할 것이다.

검증은 각각 ▲전 컬렉션 규칙의 실제 배포 및 화면 동작, ▲44종 변형 역검증의 결과, ▲규칙으로 표현 불가능한 항목의 열거와 대체 방어, ▲좁히기 전 소스 전수 조회 절차, ▲에뮬레이터 실측 5건(Q-1~Q-5)으로 확인하였다.

## *Threat Model.*

규칙을 쓰기 전에 **무엇을 막을 것인가**를 먼저 열거했다.

| # | 위협 | 막는 조건 |
|:---:|---|---|
| T1 | 외부인이 학교 계정 없이 접근 | 인증 토큰의 이메일 도메인 검사 |
| T2 | 승인 대기 계정이 업무 데이터 열람 | `status == 'active'` 요구 |
| T3 | 클라이언트가 자기 역할을 위조해 전송 | **역할은 서버에 저장된 문서에서 읽는다.** 요청 본문의 역할 값은 신뢰하지 않는다 |
| T4 | 부장이 자기 역할을 마음대로 올리거나 내림 | 본인 문서에 대한 역할 변경 차단(양도의 자기 강등만 예외) |
| T5 | 남의 이름으로 기록 작성 | `createdBy == auth.uid` 강제 |
| T6 | 기록의 학생·일시·작성자를 사후 변조 | **변경 가능 필드를 `hasOnly`로 못 박음** |
| T7 | 기록을 흔적 없이 삭제 | **물리 삭제 전면 금지.** 상태 전이(soft delete)만 |
| T8 | 감사 로그 위조·삭제 | 생성만 허용, 수정·삭제 전면 금지 |
| T9 | 가입 코드 목록 열람으로 유효 코드 유출 | **`get`과 `list`를 분리** |
| T10 | 부장이 승인 절차를 통해 코드 만료 권한을 우회 | 같은 연산에서 **필드로 권한을 가름** |

## *Rules Design.*

### *① 도메인 검사 — 실측이 문서를 고쳤다*

```
request.auth != null && request.auth.token.email.matches('.*@dshs[.]kr$')
```

명세는 정규식 끝의 `$` 앵커를 **필수 조건**으로 규정했다. 그런데 실측 결과 **막고 있는 주체가 `$`가 아니었다.**

| 정규식 | `attacker@dshs.kr.evil.com` |
|---|---|
| `.*@dshs[.]kr$` | 거부 |
| `.*@dshs[.]kr` (`$` 제거) | **거부** — 아무것도 바뀌지 않는다 |
| `.*@dshs[.]kr.*` (뒤에 `.*`) | **통과** ← 실제 급소 |

규칙 엔진의 `matches()`는 **문자열 전체 일치**이기 때문이다.
`$`는 "이 표현식이 언젠가 부분 일치 API로 옮겨 가거나 뒤에 무엇이 덧붙는 순간"을 대비한 **이중 방어**로 남기되,
**진짜 위험은 `$`의 유무가 아니라 끝에 `.*`가 붙는 것**이라고 주석에 못 박았다.

> ⚠️ **이메일 검증 상태(`email_verified`)는 검사하지 않는다.** 사용하는 인증 공급자의 토큰은 항상 검증 상태이고,
> 리다이렉트 직후 토큰 갱신 타이밍에 따라 **정상 사용자가 거부되는 사고**를 만든다.

### *② 역할은 서버가 저장한 문서에서 읽는다*

```
me()   = get(/databases/$(db)/documents/users/$(request.auth.uid)).data
role() = me().role
```

**클라이언트가 보낸 역할 값은 신뢰하지 않는다.** 요청 본문에 `role: 'head'`가 들어 있어도 규칙은 그것을 보지 않는다.

사용자 문서가 없으면(가입 전) 조회가 실패해 거부로 떨어지는데, **그것이 옳은 결과다** — 프로필이 없는 계정은 `active`가 아니다.
다만 가입 경로 세 곳(`users` 생성 · 가입 신청 생성 · 코드 조회)은 이 함수를 부르지 않도록 설계했다. 부르면 **가입 자체가 불가능해진다.**

### *③ `get`과 `list`는 분리된 권한이다*

이번 설계에서 **가장 위험했던 지점**이다. 명세의 스켈레톤은 두 연산을 `allow read`로 뭉쳐 놓았다.

| 뭉쳤을 때 | 결과 |
|---|---|
| `allow read: if 본인 이거나 부서원` | **목록 질의가 통째로 거부된다.** 부원 목록·작성자 이름 조회 화면이 죽는다 |
| `allow read: if isSignedIn()` (가입 코드) | **유효한 코드 전체가 유출된다** |

실측으로 원인을 확정했다 — `allow read: if request.auth.uid == uid` 하나만 둔 규칙에서
**단건 조회는 허용, 컬렉션 목록은 거부**였고, `where(문서ID == 본인)`으로 좁힌 질의는 통과했다.

> 즉 **질의가 규칙 조건을 스스로 증명해야 한다.** 이것이 "규칙은 필터가 아니다"의 정확한 뜻이다.
> 규칙은 목록의 결과 문서마다 평가되고, 질의가 조건과 어긋나면 **한 건도 안 주는 것이 아니라 질의 자체를 거부한다.**

가입 코드는 이 성질을 **적극적으로 이용**했다.

| 연산 | 권한 | 근거 |
|---|---|---|
| 단건 `get` | 학교 계정 전체 | 가입 신청자는 정의상 `active`가 아니다. **문서 ID가 코드 문자열 자체**라 코드를 이미 아는 사람만 1건을 읽는다 |
| `list` | 부장만 | 목록이 잠겨 있으므로 **열거가 불가능하다** |

읽어서 얻는 것도 활성 여부·만료일·사용 횟수뿐이라 개인정보가 없다.
남는 위험은 무차별 대입(4,569,760가지)이며, 그 짝은 신청 레이트 리밋과 앱 무결성 검사로 별도 배정했다.

### *④ 변경 가능 필드를 `hasOnly`로 못 박는다*

기록 수정 규칙은 "학생·일시·작성자는 못 바꾼다"를 등식 두 개로 막고 있었다. **목록 밖 필드가 조용히 열린다.**

```
diff(resource.data).affectedKeys().hasOnly(['reasonCode', 'reasonText', 'updatedBy', 'updatedAt'])
```

허용 목록에 **없는 것은 한 글자도 바뀔 수 없다.** 금지 목록이 아니라 허용 목록으로 뒤집은 것이 핵심이다 —
필드가 늘어날 때 금지 목록은 자동으로 뚫리지만 허용 목록은 자동으로 잠긴다.

같은 방식을 순찰 일정에도 적용했고, 마이그레이션이 남긴 **되돌리기용 옛 필드 4개**도 목록에서 뺐다.
앱이 읽지도 쓰지도 않는 사본이므로, 새 앱이 그것을 건드리면 되돌릴 근거가 사라지기 때문이다.

### *⑤ 물리 삭제는 없다*

```
allow delete: if false;        // 기록 · 감사 로그 · 가입 신청 · 코드
```

삭제는 상태 전이(`active → deleted`)로만 일어나며, **`dev`도 예외가 아니다.**

되돌리기(`deleted → active`)는 **열지 않았다.** 복구 UI가 없고, 여는 순간 "지운 것을 아무 흔적 없이 되살리는" 경로가 생긴다.
검증용 복구는 콘솔이 하고, 그 절차를 문서에 적었다.

삭제 사유 필드도 허용 목록에 넣지 않았다 — **지금 그것을 쓰는 입력란이 없고, 길이 검증 없이 키만 열면 임의 길이 문자열이 들어온다.**
입력란을 만드는 회차가 **키와 길이 조건을 함께** 연다.

### *⑥ 사유 변경과 삭제는 서로 배타적이다*

두 전이는 각각 자기 `hasOnly` 목록을 갖는다. 한 요청이 둘을 겸하면 **양쪽 목록이 모두 깨져 거부된다. 그것이 의도다.**

### *⑦ 필드로 권한을 가른다*

부서 문서는 두 가지 이유로 갱신된다 — 가입 코드 **재발급**과 부장 **양도**. **그런데 권한이 다르다.**

```
allow update: if
     (isDev()  && affectedKeys().hasOnly(['activeInviteCodeId', 'updatedAt']))
  || (isHead() && affectedKeys().hasOnly(['headUid',            'updatedAt']));
```

넓은 쪽(`isHead()`)으로 뭉치면 부장이 여전히 코드를 재발급할 수 있어 통제가 성립하지 않는다.
가를 수 있었던 근거는 **두 배치의 실제 페이로드가 정확히 두 형태**이고 겹치는 키가 하나뿐이라는 소스 실측이다.

**두 필드를 한 번에 바꾸는 요청은 양쪽 목록이 다 깨져 거부된다** — 우회로를 남기지 않는다.
같은 급소가 가입 코드에도 있다: 부장의 승인이 사용 횟수를 +1 해야 하므로 갱신을 완전히 잠글 수 없는데,
그 문으로 **만료 처리를 끼워 넣는 경로**를 `hasOnly`가 막는다.

### *⑧ 감사 로그는 불변이다*

```
allow create: if isSignedIn() && request.resource.data.actorUid == request.auth.uid;
allow update: if false;
allow delete: if false;
```

**자기 uid로만 남길 수 있고, 남긴 뒤에는 아무도 고칠 수 없다. 고쳐질 수 있으면 감사가 아니다.**

### *⑨ 기본 거부 — catch-all을 일부러 두지 않았다*

규칙 엔진은 어떤 `match`도 허용하지 않으면 거부한다. 그래서 `match /{document=**} { allow read, write: if false; }`를 **넣지 않았다.**

동작은 같지만, 그 블록은 개발기 임시 규칙(`@dshs.kr`이면 전부 허용)과 **모양이 똑같다.**
나중에 누가 `if false`를 `if isSignedIn()`으로 **한 글자** 고치는 순간 전 컬렉션이 다시 열린다.
**있는 그대로의 부재가 더 안전한 경우다.**

### *⑩ 인덱스에서 개인정보를 뺀다*

규칙 밖의 방어도 하나 두었다. 학생 이름·자유 기입 사유·이메일·표시 이름은 **단일 필드 인덱스를 명시적으로 제거**했다.
인덱스가 없으면 그 필드로는 정렬·범위 질의를 만들 수 없다 — 규칙이 열려 있는 컬렉션에서도 **질의로 훑는 경로가 줄어든다.**

## *Measurement.*

규칙의 구조를 결정한 것은 명세가 아니라 **에뮬레이터 실측 5건**이다.

### *Q-1 — 목록 질의에서 경로 와일드카드 조건을 쓸 수 있는가*

**없다.** 단건은 허용, 목록은 거부. 질의가 조건을 스스로 증명해야 한다. → ③의 근거

### *Q-2 — 배치 안의 `get()`은 배치 이전 상태를 보는가*

**이전 상태를 본다.** 이것이 양방향으로 작동한다.

| 상황 | 결과 |
|---|---|
| 부장 양도 배치에서 본인을 강등하면서 부서 문서도 고칠 때 | 부서 규칙의 권한 판정이 **아직 부장으로 읽혀 통과한다** ✅ |
| "부서 문서가 이미 갱신되었을 것"을 조건으로 걸면 | 배치가 **자기 자신을 거부한다** ❌ (통과하는 경로가 아예 없다) |

즉 **"배치 안에서 자기 권한을 먼저 버리면 뒤 연산이 죽는다"는 걱정은 성립하지 않고,
반대로 형제 연산의 결과를 조건으로 거는 설계는 불가능하다.**

### *Q-3 — 배치의 한 연산이 거부되면 나머지는*

**전부 되돌아간다.** 3연산 중 1개가 거부되면 남은 문서가 **0/2**였다.
"4연산 중 3개만 통과"하는 중간 상태는 없다 — 규칙이 표현하지 못하는 불변식을 **배치의 원자성**으로 보완할 수 있다는 근거다.

### *Q-4 — 규칙 안 조회의 횟수와 과금*

| 관측 | 값 |
|---|---|
| 한 연산 평가 안에서 **같은 문서** | 몇 번 참조해도 **1회** (15회 참조 통과) |
| **서로 다른** 문서 | **연산당 10건**이 상한 (11번째에서 오류) |
| 상한의 적용 단위 | **연산마다.** 4연산 배치 × 6건(합계 24)도 통과 |

⇒ 가장 무거운 승인 4연산 배치가 **4읽기**, 기록 저장 2연산은 **1읽기**다.
헬퍼 함수를 한 규칙에서 몇 번 부르든 **문서가 같으면 1읽기**이므로, 가독성을 위해 함수를 나누는 비용이 0이다.

### *Q-5 — 도메인 정규식에서 `$`가 실제로 막는 것*

→ ①에 서술. **명세의 필수 조건이 지목한 것과 실제 급소가 달랐다.** → **가설 5 지지**

## *Verification.*

### *통과만 재는 검증은 무효다*

> **"허용되어야 할 것이 허용된다"만 확인하면, 조건을 아예 쓰지 않은 규칙도 통과한다.**

그래서 검증을 두 겹으로 만들었다.

**1겹 — 케이스 검증.** 에뮬레이터 위에서 5개 스위트, **250 케이스**.

| 스위트 | 케이스 | 내용 |
|---|:---:|---|
| `records` | 51 | 생성 10항목 + 경계, 읽기, 사유 변경 권한 4종, 소프트 삭제 |
| `users` | 74 | 목록/단건 분리, 도메인 3중 방어, 승인·거절, 역할 변경, 재신청 6조건, 탈퇴 |
| `admin` | 71 | 가입 신청, 가입 코드, 감사 로그, 순찰 일정, 명단, `meta` |
| `batches` | 47 | 승인 4연산 · 거절 3연산 · 재발급 · 양도 · 가입 · 저장 · 탈퇴 · 일정 |
| `recordCount` | 7 | 카운터 증가 상한 |
| **합계** | **250** | **거부 157 / 허용 93** |

**거부가 허용의 1.7배다.** 규칙 테스트의 본체는 "된다"가 아니라 "안 된다"이기 때문이다.

픽스처는 **규칙을 끄고 심는다.** 규칙을 통과시켜 심으면 테스트가 검증 대상에 의존하게 되고,
규칙이 넓어졌을 때 픽스처가 함께 통과해 **결함을 가린다.**

**2겹 — 변형 역검증(mutation).** 규칙의 조건을 **하나씩 일부러 열고** 돌려서, 그 조건을 지키던 테스트가 실제로 빨개지는지 본다.
빨개지지 않으면 **그 조건은 아무 일도 하고 있지 않다는 뜻**이다.

**44종의 변형**을 정의하고 각각이 깨뜨려야 할 케이스 ID를 선언했다.

| 변형 | 여는 것 | 깨져야 할 케이스 |
|---|---|---|
| `domain-suffix-open` | 도메인 정규식 끝에 `.*` | 도메인 방어 1건 |
| `self-role-free` | 부장의 본인 역할 변경 차단 제거 | 5건 |
| `records-reason-free` | 사유 유효성 검사 제거 | 6건 |
| `auditlogs-mutable` | 감사 로그 수정 허용 | 3건 |
| `reason-keys-open` | 사유 변경의 `hasOnly` 제거 | 4건 |
| `departments-field-split-off` | 필드 분기 제거 | 4건 |
| `duty-keys-open` | 일정의 `hasOnly` 제거 | 5건 |
| `no-dollar-anchor` | 정규식 끝의 `$` 제거 | **0건 — 아무것도 안 깨지는 것이 정답** |

마지막 변형이 이 방법론의 성격을 보여준다. **"아무것도 빨개지지 않는다"가 기대값으로 선언된 변형**이 있고,
그것이 곧 "`$`는 혼자서는 아무것도 막지 않는다"는 실측 결론의 자동화된 형태다.

역검증은 규칙 파일을 임시로 고쳐 돌린 뒤 **바이트 사본에서 자동 원복**한다.
줄바꿈은 양쪽 모두 정규화한다 — 한쪽만 정규화하면 개행 설정이 다른 환경에서 조각을 영원히 찾지 못한다.

### *역검증이 실제로 잡은 것*

선언된 "깨져야 할 케이스" 목록 자체가 두 번 틀렸다.
권한을 좁히는 회차에서 새 배치 케이스를 추가하면서 **기존 변형의 선언을 갱신하지 않았고**,
역검증을 돌렸을 때 선언에 없던 케이스가 함께 빨개져 발견되었다.

**변형이 검사한 것은 규칙만이 아니라 "규칙과 테스트의 대응 관계"였다.**

## *Limits of Rules.*

규칙이 **끝까지 보장하지 못하는 것**을 문서로 남기는 것도 설계의 일부였다.

| # | 표현할 수 없는 것 | 이유 | 대체 방어 |
|:---:|---|---|---|
| ① | "부장은 정확히 1명" | 규칙 안에서 **집합 질의를 할 수 없고** 조회는 문서 1건만 본다 | 역할 변경 권한 제한 + 배치 원자성(Q-3) + 복구 경로 |
| ② | "감사 로그 없이는 수정도 실패" | 규칙은 **형제 연산을 볼 수 없다**(Q-2) | 배치 원자성. 배치를 만드는 것은 앱 코드 |
| ③ | 필드 단위 읽기 제한 | `allow read`는 **문서 단위**다 | 규칙은 부서원에게 열고, "이름·역할만 그린다"는 클라이언트 규율이 맡는다 |
| ④ | "이번 주 또는 다음 주만" | 규칙에 **주차를 계산할 수단이 없다** | 화면이 막는다 |
| ⑤ | 카운터를 단독으로 부풀리는 요청 | 형제 연산을 못 봄. 상한이 "한 번에 +1"이라 남용해도 자기 값만 부푼다 | 그 값은 지표에만 쓰인다. 실질 차단은 서버 함수 |
| ⑥ | 동시 양도 경쟁 | 규칙에 트랜잭션 개념이 없다 | 서버 함수로 이관 |

> **③은 특히 정직하게 적어야 할 항목이다.** 규칙이 부서원 전체에게 사용자 문서를 열어 준다는 것은
> "이메일을 안 그린다"가 **규칙이 아니라 약속**이라는 뜻이다. 실제로 그리지 않음을 화면 실측으로 확인했지만,
> 이것은 규칙이 강제하는 것이 아니다. → **가설 3 지지**

## *Result.*

| 항목 | 결과 |
|---|---|
| 전 컬렉션 규칙 적용 | 임시 catch-all을 **전량 교체** |
| 케이스 검증 | **250건** (거부 157 / 허용 93) |
| 변형 역검증 | **44종** — 선언된 깨짐 케이스와 실제 결과 대조 |
| 실측 항목 | 5건 (Q-1 ~ Q-5) |
| 롤백 원본 | 임시 규칙을 별도 파일로 보존 |
| 배포 규모 | 부원 약 40명 · 학생 명단 전교 |

### *롤백 경로를 함께 만들었다*

이 규칙 파일은 **저장소의 첫 커밋**이라 이력에 이전 버전이 없다.
표준 롤백 절차("이전 버전 재배포")가 성립하지 않으므로, 임시 개발 규칙을 별도 파일로 남기고
**"되돌리는 절차"와 "되돌린 뒤 무엇을 해야 하는지"** 를 함께 문서화했다.
그 파일에는 `🔴 되돌린 상태로 오래 두지 마라`가 첫 줄에 적혀 있다.

### *권한을 좁힐 때는 소비자를 먼저 센다*

순찰 일정 편성 권한을 차장 이상 → 부장으로 좁히기 전에, **앱 소스에서 그 컬렉션을 만지는 곳을 전수 조회**했다.
쓰기 경로가 0건임을 확인한 뒤에 좁혔다 — **좁혀도 깨질 화면이 없다는 것을 배포 전에 알았다.**

반대로 가입 신청 목록에 "본인" 절을 **더한** 회차에서는, 옛 앱이 그 질의를 만들지 않으므로
**규칙을 앱보다 먼저 배포해도 깨지는 화면이 없다**고 판정했다.
넓히기와 좁히기는 배포 순서가 반대다. → **가설 4 지지**

### *규칙과 화면은 같은 문장이어야 한다*

기록 수정 권한은 규칙과 화면 코드 **양쪽에 같은 판정 함수**로 존재한다.
한쪽만 고치면 **"눌렀는데 실패"** 하거나 **"할 수 있는데 버튼이 안 보인다"** 가 된다.
실제로 그 형태의 결함이 한 번 발생했고, 이후 두 함수는 서로가 사본임을 주석으로 명시했다.

## *Conclusion*

1. **서버 없는 구조에서 규칙은 유일한 방어선이다.** 화면에서 버튼을 숨기는 것은 방어가 아니다. 역할·상태·필드 조건을 규칙에 표현함으로써 애플리케이션 서버 없이 조직의 권한 체계를 강제할 수 있었다. → **가설 1 지지**
2. **통과만 재는 검증은 무효다.** 조건을 아예 쓰지 않은 규칙도 통과 테스트는 전부 지나간다. 조건을 하나씩 열고 **빨개지는지** 보는 역검증이 붙어야 그 조건이 일하고 있다는 증거가 된다. → **가설 2 지지**
3. **`allow read`를 뭉치지 마라.** 단건 조회와 목록 조회는 서로 다른 권한이다. 뭉치면 화면이 죽거나 데이터가 새며, **둘 중 어느 쪽인지는 조건의 모양이 정한다.**
4. **금지 목록이 아니라 허용 목록으로 쓴다.** `hasOnly`는 필드가 늘어나도 자동으로 잠기지만, 개별 등식은 필드가 늘어나면 자동으로 뚫린다.
5. **규칙이 못 하는 것을 적는 것도 설계다.** 집합 불변식·형제 연산·필드 단위 읽기 제한은 규칙의 표현력 밖이며, 그것을 모른 채 "규칙이 막고 있다"고 믿는 것이 가장 위험하다. 여섯 항목을 열거하고 각각의 대체 방어를 배정했다. → **가설 3 지지**
6. **명세와 엔진이 어긋난다.** 필수 조건이 지목한 방어(`$` 앵커)가 실제로는 아무것도 막지 않았고, 진짜 급소는 다른 곳(`.*` 접미)이었다. 실측 없이 문서만 따랐다면 잘못된 것을 지키고 있다고 믿었을 것이다. → **가설 5 지지**
7. **주석은 코드의 일부다.** 이 규칙 파일에서 조건보다 주석이 길다. 「왜 이 조건인가」가 사라지면 다음 사람이 되돌리기 때문이다. 되돌리면 안 되는 조건에는 그 이유와 함께 **되돌렸을 때 무엇이 뚫리는지**를 적었다.

## *Limit & Plan*

- **집합 불변식은 여전히 미보장** — "부장 정확히 1명"과 동시 양도 경쟁은 규칙으로 닫히지 않는다. 서버 함수(트랜잭션)로 이관이 필요하다.
- **필드 단위 읽기 제한 부재** — 사용자 문서가 부서원에게 전 필드로 열려 있다. "이름·역할만 그린다"는 클라이언트 규율이며 강제가 아니다. 민감 필드를 하위 문서로 분리하는 스키마 변경이 근본 해법이다.
- **가입 코드 무차별 대입** — 목록은 잠겼지만 단건 조회는 학교 계정 전체에 열려 있다. 신청 레이트 리밋과 앱 무결성 검사가 배포 회차로 이관된 상태다.
- **역검증의 선언은 손으로 관리된다** — "이 변형은 이 케이스를 깨야 한다"는 목록이 사람이 적는 값이라, 실제로 두 번 누락되었다. 자동 수집(변형별 실제 실패 목록을 스냅샷으로 고정)이 다음 개선점이다.
- **규칙 안 조회의 상한** — 연산당 서로 다른 문서 10건이 상한이다. 부원 40명 규모에서는 문제가 없지만, 역할 판정에 부서 문서까지 끌어들이는 조건을 추가하면 상한에 접근한다.
- **감사 로그의 무결성은 배치 원자성에 의존한다** — 로그 없이 기록만 고치는 경로를 규칙이 직접 막지 못한다. 배치를 만드는 것은 앱 코드이므로, **앱을 우회한 SDK 직접 호출**에서는 로그 없는 수정이 가능하다. 서버 함수 이관 대상이다.

### *Term.*

- **RLS (Row Level Security)** — 행(문서) 단위로 접근을 판정하는 방식. 이 프로젝트는 문서 데이터베이스의 보안 규칙으로 같은 목적을 달성한다
- **보안 규칙(Security Rules)** — 데이터베이스가 요청마다 평가하는 선언적 접근 제어. 클라이언트가 우회할 수 없다
- **"규칙은 필터가 아니다"** — 규칙은 조건에 맞는 문서만 골라 주지 않는다. 질의가 조건을 증명하지 못하면 **질의 전체를 거부**한다
- **`get` / `list`** — 단건 조회 / 컬렉션 질의. **서로 다른 권한**이며 `allow read`는 둘을 뭉친 것이다
- **`hasOnly`** — 이번 요청에서 값이 바뀐 키가 주어진 목록 안에 전부 들어 있는지 검사. 허용 목록 방식의 필드 잠금
- **`affectedKeys()`** — **값이 실제로 바뀐** 키의 집합. 같은 값을 다시 써도 포함되지 않는다
- **소프트 삭제(soft delete)** — 문서를 지우지 않고 상태 필드를 전이시켜 "삭제됨"으로 표시하는 방식. 감사 추적을 남긴다
- **감사 로그(audit log)** — 누가 언제 무엇을 했는지의 불변 기록. 수정·삭제가 가능하면 감사로서 성립하지 않는다
- **배치(batch)** — 여러 문서 쓰기를 하나로 묶는 연산. **원자적**이라 한 연산이 거부되면 전부 되돌아간다
- **변형 테스트(mutation testing)** — 검증 대상을 일부러 망가뜨리고, 테스트가 그것을 잡아내는지 보는 방법. 테스트의 유효성을 테스트한다
- **기본 거부(deny by default)** — 명시적으로 허용되지 않은 모든 접근을 거부하는 원칙
- **인덱스 면제(index exemption)** — 특정 필드의 단일 필드 인덱스를 제거해 그 필드로 질의를 만들 수 없게 하는 설정
- **위협 모델(threat model)** — 무엇을, 누구로부터, 어떤 경로로 막을 것인가를 먼저 열거하는 설계 절차
