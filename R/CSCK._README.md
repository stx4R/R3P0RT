# CSCK.

**공용 태블릿 한 대로 수백 명이 지나가는 현장**을 전제로, 출석체크 키오스크의 UI/UX를 사용자 경험에서 역산해 설계한 프로젝트.
"처음 보는 사람이 설명 없이 3초 안에 끝낼 수 있는가"를 유일한 기준으로 삼아 화면을 짰고,
백엔드 유무·기기 종류·네트워크 상태와 무관하게 **같은 빌드 하나가 그대로 동작하는** 웹앱으로 구현하였다.

---

## *Motive.*

행사 현장의 출석체크는 대개 종이 명단과 볼펜으로 이루어진다.
줄이 길어지고, 누가 왔는지 실시간으로 알 수 없으며, 행사가 끝난 뒤에 명단을 다시 옮겨 적어야 한다.

전자화 자체는 새로운 발상이 아니다. 문제는 **전자화한 것이 종이보다 느려지는 경우가 흔하다**는 점이다.
앱을 설치하라고 하면 줄이 멈추고, 로그인을 요구하면 줄이 더 멈추며,
QR을 나눠 주면 QR을 잃어버린 사람에서 줄이 완전히 멈춘다.

### *제약이 설계를 정했다*

| 제약 | 설계에 미친 영향 |
|---|---|
| **기기가 공용이다** | 로그인이 없다. 개인 계정을 전제할 수 없다 |
| **사용자가 매번 바뀐다** | **학습이 불가능하다.** 두 번째 사용이 첫 번째보다 빠를 수 없다 |
| **줄이 서 있다** | 한 사람의 지연이 뒤 전체의 지연이다. **막다른 길이 있으면 안 된다** |
| **운영자가 붙어 있지 않다** | 설명 없이 완결되어야 하고, **잘못 눌러도 복구 가능**해야 한다 |
| **현장 네트워크를 신뢰할 수 없다** | 서버가 죽어도 접수는 계속되어야 한다 |

> 🎯 **설계 기준**
> **처음 보는 사람이, 설명 없이, 3초 안에 끝낸다.**
> 이 문장에 기여하지 않는 기능은 넣지 않는다.

### *Purpose.*

사용자가 **무엇을 해야 하는지 배우지 않아도 되는** 키오스크 인터페이스를 설계하고,
그 인터페이스가 **어떤 배포 환경에서도 동일하게 동작**하도록 만드는 것을 목적으로 한다.
동시에 현장에서 반드시 발생하는 예외(명단에 없는 사람, 중복 시도, 오터치, 네트워크 단절)를
**막다른 길로 만들지 않는 경로**를 각각 마련한다.

## *Research Q & H.*

> 학습이 불가능한 사용자를 전제로 UI를 설계할 수 있는가? 그리고 그 앱이 환경을 가리지 않게 만들 수 있는가?

- **가설 1 (입력 최소화)** — 식별자를 처음부터 끝까지 입력하게 하는 대신 **입력할수록 후보가 좁혀지는 방식**을 쓰면, 사용자는 자신이 언제 멈춰도 되는지를 화면에서 스스로 판단할 것이다.
- **가설 2 (오터치 방어)** — 공용 대형 화면에서 실수는 **예외가 아니라 상시 조건**이다. 확인 단계를 넣어 생기는 지연보다 잘못된 기록을 되돌리는 비용이 클 것이다.
- **가설 3 (막다른 길 제거)** — 명단에 없는 사용자를 거부하면 그 지점에서 줄이 멈춘다. **예외 경로를 정상 경로 안에 두되 기록에 표시**하면, 현장 처리와 사후 정합성을 동시에 얻을 것이다.
- **가설 4 (상태 자동 복귀)** — 다음 사용자가 화면을 초기화하는 조작을 해야 한다면 그 조작 자체가 학습 대상이 된다. **시간 기반 자동 복귀**가 필요할 것이다.
- **가설 5 (환경 무관 단일 빌드)** — 데이터 계층을 한 파일로 격리하면, 백엔드 설정의 유무만으로 데모·개발·운영 세 환경이 **같은 코드에서** 갈릴 것이다.

검증은 각각 ▲자릿수 입력에 따른 후보 수 실시간 표시, ▲확인 카드와 터치 가드의 동작, ▲예외 경로의 기록 구분 및 대시보드 별도 집계, ▲성공 후 자동 초기화 동작, ▲환경변수 유무에 따른 자동 전환으로 확인하였다.

## *UX Design.*

### *① 점진적 좁힘 — 사용자가 멈출 시점을 스스로 안다*

식별자로 전화번호를 쓰되, **전부 입력하게 하지 않는다.**
한 자리를 누를 때마다 명단이 접두 일치로 걸러지고, 남은 후보 수가 입력란 오른쪽에 **실시간으로 표시**된다.

```
010-        → 전체
010-1       → 12명
010-12      → 3명
010-123     → 1명    ← 여기서 멈추면 된다
```

전부 입력하라고 지시하지 않는다. **후보 목록에 자기 이름이 보이는 순간이 곧 멈추는 시점**이고,
그 판단을 화면이 대신 내려 주지 않는다. 사용자는 지시를 따르는 것이 아니라 결과를 보고 행동한다.

목록의 각 행에는 **지금까지 입력한 자릿수를 강조색으로, 나머지를 흐린 색으로** 인쇄한다.
"왜 이 사람이 여기 나왔는가"가 설명 없이 읽힌다. → **가설 1 지지**

### *② 이미 끝난 사람을 목록에서 지우지 않는다*

출석이 끝난 사용자는 목록에서 사라지지 않고, `출석체크` 버튼이 **`출석 완료` 배지로 바뀐 채 남는다.**

지우는 편이 목록은 짧아진다. 그런데 **이미 체크한 사람이 다시 와서 자기 이름을 못 찾으면 불안해진다** —
"내가 한 게 맞나?"를 확인할 방법이 사라지고, 그 사람은 운영자를 찾는다. **줄이 멈춘다.**

남겨 두면 그 자리에서 확인이 끝난다. 눌러도 기록이 추가되지 않고 안내만 뜬다.

### *③ 확인 단계 — 오터치는 예외가 아니라 상시 조건이다*

대형 화면에서 손가락이 옆 행을 스치는 일은 **반드시 일어난다.**
행을 누르면 곧바로 기록되지 않고 **이름을 크게 인쇄한 확인 카드**가 뜬다.

```
[아무개]님으로
출석체크를 하시겠습니까?

        [아니요]  [네]
```

한 번의 탭이 추가되지만, 잘못된 기록을 사후에 찾아 지우는 비용과 비교할 수 없다.
확인 카드는 대상 이름을 **가장 큰 글자로** 인쇄한다 — 확인의 대상이 "출석체크를 할 것인가"가 아니라 **"이 사람이 맞는가"** 이기 때문이다. → **가설 2 지지**

### *④ 막다른 길을 만들지 않는다*

명단에 없는 사람은 현장에서 반드시 나온다. 거부하면 그 지점에서 줄이 멈춘다.

| 단계 | 화면 |
|---|---|
| 일치 없음 | 붉은 안내 — "일치하는 사람이 없습니다. **강제로 진행하시겠습니까?**" |
| 확장 | 이름 입력란 + 이미 입력한 번호를 그대로 이어받는 패널 |
| 기록 | 정상 경로와 같은 저장소, **`강제` 플래그를 세워서** |

**예외를 정상 경로 밖으로 내보내지 않되, 기록에는 반드시 남긴다.**
관리자 화면은 이 플래그로 별도 집계하며, 정상 체크와 강제 체크가 **같은 이름으로 둘 다 존재하는 경우**를 다른 색으로 구분한다.
현장은 막히지 않고, 사후 정합성 확인은 가능해진다. → **가설 3 지지**

이름조차 모르면 `(이름 미입력)`으로 기록된다. **접수를 거부하는 것보다 불완전하게 기록하는 편이 낫다** —
현장에서 놓친 사람은 영원히 복구할 수 없지만, 불완전한 기록은 나중에 채울 수 있다.

### *⑤ 성공 화면은 스스로 사라진다*

기록이 저장되면 체크 애니메이션과 색종이 효과가 재생되고, **3초 뒤 모든 상태가 자동으로 초기화**된다.
입력한 숫자, 열려 있던 키패드, 확장된 패널이 전부 닫힌다.

다음 사용자가 "이전 사람의 화면을 지우는 방법"을 알 필요가 없다.
**그 조작을 요구하는 순간 그것이 학습 대상이 되고, 학습은 불가능하다는 것이 이 프로젝트의 전제였다.** → **가설 4 지지**

성공 연출을 넣은 것도 기능이다. 화면이 조용히 목록으로 돌아가면 **사용자는 자기 조작이 반영됐는지 확신하지 못하고 한 번 더 누른다.**
과장된 피드백은 장식이 아니라 **재시도를 막는 장치**다.

### *⑥ 탈출구는 항상 같은 자리에 있다*

헤더 로고 영역이 **"처음 화면으로"** 버튼이다. 어느 상태에서 눌러도 전부 초기화된다.
사용자가 길을 잃었을 때 찾는 곳은 화면 왼쪽 위이고, 그 관습을 따랐다.

키패드는 **바깥을 탭하면 닫힌다.** 닫기 버튼을 찾을 필요가 없다.
다만 목록·확인 카드·키패드 내부의 탭은 이벤트가 위로 전파되지 않도록 각각 차단했다 —
**"바깥을 누르면 닫힌다"가 "아무 데나 누르면 닫힌다"가 되면 목록을 못 누른다.**

### *⑦ 중복 저장은 3중으로 막는다*

| 층 | 방어 |
|---|---|
| 연타 | 저장 중 플래그로 **두 번째 요청 자체를 차단** |
| 클라이언트 | 이미 기록된 사용자 집합과 대조 |
| 데이터베이스 | 유일 제약 위반 코드를 받아 **중복 안내로 변환** |

앞의 두 층은 사용자 경험(즉시 반응)이고, 마지막 층은 **정합성**이다.
클라이언트 검사는 다른 기기가 방금 저장한 것을 모르므로, 최종 판정은 반드시 데이터베이스가 한다.
두 기기를 나란히 놓고 운영하는 상황에서 이 층이 없으면 같은 사람이 두 번 기록된다.

### *⑧ 터치 가드 — 웹을 앱처럼 만드는 실무*

브라우저의 기본 동작 상당수가 키오스크에서는 결함이 된다.

| 기본 동작 | 조치 | 이유 |
|---|---|---|
| 핀치 줌 | 제스처 이벤트 차단 | 화면이 확대된 채 남으면 다음 사용자가 복구하지 못한다 |
| 더블탭 줌 | `touch-action: manipulation` | 연타를 확대로 오인하면 조작이 씹힌다 |
| 길게 눌러 복사·공유 | 콜아웃·컨텍스트 메뉴 차단 | **입력란은 예외** — 거기서는 편집이 되어야 한다 |
| 텍스트 드래그 선택 | `user-select: none` | **입력란은 예외** |
| 이미지 드래그 | 드래그 차단 | 로고를 끌어다 놓는 사고를 막는다 |
| 탭 하이라이트 | 투명 처리 | 회색 사각형이 번쩍이면 조작감이 깨진다 |

**예외를 명시적으로 뚫어 놓은 것이 요점이다.** 전역으로 잠그기만 하면 이름 입력이 불가능해진다.

## *Universality.*

### *① 같은 빌드가 세 환경에서 돈다*

데이터 계층을 파일 하나로 격리하고, **백엔드 설정의 유무만으로** 동작이 갈리게 했다.

| 환경 | 명단 | 기록 저장 | 실시간 갱신 |
|---|---|---|---|
| 설정 없음 (데모·개발) | 내장 명단 | 브라우저 로컬 저장소 | 저장소 이벤트 + 폴링 |
| 설정 있음 (운영) | 원격 테이블 | 원격 테이블 | 변경 구독 + 폴링 |

호출부는 두 경우를 구분하지 않는다. 화면 코드에 분기가 **한 줄도 없다.**

이것이 실무에서 갖는 의미는 크다 —
**행사 전날 노트북에서 그대로 리허설할 수 있고, 서버 설정이 끝나기 전에 화면을 완성할 수 있으며,
발표·시연에서 인터넷 없이 동작을 보일 수 있다.** → **가설 5 지지**

### *② 상태를 숨기지 않는다*

로컬 저장 모드로 동작 중일 때 헤더에 경고색 문구가 뜬다 —
**"오프라인 모드 · 기록이 이 기기에만 저장됩니다."**

조용히 로컬에 저장하는 것이 최악이다. 운영자는 서버에 쌓이고 있다고 믿고, 행사가 끝난 뒤에 알게 된다.
**폴백은 편의지 은폐가 아니다.**

### *③ 실시간 갱신을 이중화한다*

관리자 화면은 변경 구독으로 즉시 갱신되지만, **폴링을 함께 돌린다.**
구독은 네트워크가 잠깐 끊기면 조용히 죽고, 죽었다는 사실이 화면에 나타나지 않기 때문이다.

또한 **화면 복귀 시점마다** 다시 읽는다 — 탭 가시성 변경, 창 포커스, 온라인 복귀 세 이벤트.
키오스크 태블릿은 **화면이 꺼졌다 켜지는 것이 정상 운영**이고, 그때 구독이 끊겨 있는 경우가 흔하다.

갱신 시에는 직전 결과와 **직렬화 결과를 비교**해 실제로 달라졌을 때만 상태를 바꾼다.
폴링이 있는 이상 이 비교가 없으면 화면이 주기적으로 다시 그려진다.

### *④ 관리자 화면은 서버에서 잠근다*

| 층 | 방식 |
|---|---|
| 접근 차단 | **미들웨어(서버 측)** 가 인증 쿠키 없는 접근을 잠금 화면으로 보낸다 |
| 검증 | 서버 라우트가 비밀번호를 **서버에서만** 대조한다 |
| 세션 | `HttpOnly` 쿠키. 유효 기간을 두어 자동 만료 |
| 비밀번호 | **서버 전용 환경변수.** 클라이언트 번들에 포함되지 않는다 |
| 대조 | 평문 비교가 아니라 해시 비교 |

클라이언트에서 비밀번호를 검사하는 방식은 **번들을 열어 보면 그대로 보인다.**
잠금이 화면 전환이 아니라 **서버 응답**이어야 하는 이유다.

잠금 화면은 본 화면과 같은 키패드 컴포넌트를 쓴다. 자릿수를 채우면 **자동 제출**되고,
실패하면 카드가 좌우로 흔들리며 입력이 지워진다 — 오류 메시지를 읽지 않아도 실패가 전달된다.

### *⑤ 위험한 조작은 기본적으로 잠겨 있다*

기록 전체 삭제는 **기본 설정에서 익명 키로 차단**되어 있다.
행사 당일에 실수로 눌러 전부 지우는 것보다, 필요할 때 설정을 한 줄 여는 편이 안전하다.

차단되어 실패했을 때 **"실패했습니다"로 끝내지 않는다.** 왜 막혔고 어떻게 열 수 있는지를 그 자리에서 안내한다.
운영자가 현장에서 검색할 수 없다는 것을 전제로 한 문구다.

### *⑥ 홈 화면 설치로 앱이 된다*

브라우저에서 **홈 화면에 추가**하면 주소 표시줄 없는 전체화면으로 뜬다.
앱 스토어 심사도, 설치 파일 배포도, 기기 등록도 없다.
**웹 주소 하나만 알면 어떤 기기든 그 자리에서 키오스크가 된다.**

## *Result.*

| 항목 | 결과 |
|---|---|
| 화면 | 출석체크(키오스크) / 잠금 / 관리자 대시보드 |
| 예외 경로 | 명단 불일치 → 강제 접수 · 중복 시도 → 안내 · 오터치 → 확인 카드 |
| 데이터 계층 | 파일 하나. 원격 ↔ 로컬 자동 전환, 호출부 분기 0 |
| 런타임 의존성 | 4개 (프레임워크 3 + 백엔드 SDK 1) |
| 인증 | 서버 미들웨어 + `HttpOnly` 쿠키 + 서버 전용 비밀번호 |
| 실시간 | 변경 구독 + 폴링 + 복귀 이벤트 3종 이중화 |

### *반복 개정으로 다듬어진 것*

버전 이력을 보면 **가장 많이 고쳐진 파일이 화면과 스타일**이다.
한 회차에서는 대시보드와 스타일시트를 각각 200줄 이상 다시 썼는데, 기능 추가가 아니라 **정리**였다 —
같은 요소가 화면마다 조금씩 다르게 생긴 것을 하나로 맞추는 작업이다.

키오스크에서 이것은 미관 문제가 아니다. **같은 것이 같게 생기지 않으면 사용자는 그것을 다른 것으로 읽는다.**

## *Conclusion*

1. **학습 불가능성을 전제로 하면 설계 기준이 단순해진다.** "두 번째 사용이 첫 번째보다 빠를 수 없다"를 받아들이면, 튜토리얼·설정·기억되는 상태가 전부 무의미해진다. 남는 것은 **지금 화면에 보이는 것뿐**이고, 그것만으로 끝나야 한다.
2. **입력을 요구하지 말고 좁혀 준다.** 전화번호를 전부 받는 대신 자릿수마다 후보를 좁히고 그 수를 보여주면, 사용자는 지시를 따르지 않고 **결과를 보고 스스로 멈춘다.** → **가설 1 지지**
3. **확인 단계의 비용은 오기록의 비용보다 싸다.** 공용 대형 화면에서 오터치는 예외가 아니라 상시 조건이며, 탭 한 번을 아끼려다 사후 정정 비용을 치른다. → **가설 2 지지**
4. **막다른 길이 곧 병목이다.** 명단에 없는 사람을 거부하면 그 자리에서 줄 전체가 멈춘다. 예외를 정상 경로 안에 두되 **기록에 표시**하면 현장 처리와 사후 정합성을 둘 다 얻는다. → **가설 3 지지**
5. **다음 사용자를 위한 초기화는 앱이 해야 한다.** 그것을 사용자에게 맡기는 순간 학습 대상이 하나 늘어난다. 성공 연출도 장식이 아니라 **재시도를 막는 피드백**이다. → **가설 4 지지**
6. **데이터 계층 하나를 격리한 것이 범용성의 전부였다.** 화면 코드에 환경 분기가 없기 때문에 데모·개발·운영이 같은 빌드에서 갈린다. 다만 **폴백 상태는 반드시 화면에 표시해야 한다** — 조용한 폴백은 편의가 아니라 사고다. → **가설 5 지지**
7. **잠금은 화면 전환이 아니라 서버 응답이어야 한다.** 클라이언트에서 비밀번호를 대조하는 방식은 번들을 열면 그대로 보인다. 미들웨어·`HttpOnly` 쿠키·서버 전용 환경변수 셋이 함께 있어야 성립한다.

## *Limit & Plan*

- **표준 PWA 요건은 미충족이다** — 현재는 웹앱 메타 태그를 통한 홈 화면 설치까지이며, **웹 매니페스트와 서비스워커가 없다.** 따라서 설치 아이콘·시작 URL·표시 모드가 플랫폼별로 다르게 해석되고, **오프라인 동작은 로컬 저장 폴백에 한정**된다(앱 자체를 캐싱하지 않으므로 첫 로드에는 네트워크가 필요하다). 진짜 오프라인 키오스크가 되려면 이 둘이 먼저다.
- **화면 폭이 고정되어 있다** — 최소 폭을 크게 잡아 가로형 태블릿·데스크톱을 전제한다. 세로 태블릿과 휴대폰에서는 레이아웃이 성립하지 않는다. "어떤 기기든 된다"는 아직 **가로 대화면에 한정된 진술**이다.
- **확대 차단은 접근성과 맞바꾼 값이다** — 키오스크 조작감을 위해 확대를 막았고, 이는 저시력 사용자의 확대 요구와 충돌한다. 본문 크기를 크게 유지해 완화했으나 근본 해결은 아니다.
- **명단이 빌드에 포함된다** — 폴백용 내장 명단이 소스에 있어 저장소를 여는 사람이 전부 볼 수 있다. 개인정보가 포함될 경우 이 방식은 유지될 수 없으며, 폴백을 **빈 명단 + 수동 입력**으로 바꾸는 것이 안전하다.
- **기록 수정·삭제 UI가 없다** — 잘못 들어간 기록은 관리 콘솔에서 직접 지워야 한다. 강제 접수 기록을 사후에 정상 기록으로 승격시키는 화면이 있으면 예외 경로가 완결된다.
- **접근성 검증 미실시** — 색 대비, 스크린 리더, 키보드 조작을 측정하지 않았다. 키오스크라는 이유로 생략했지만, 공공 성격의 접수 단말은 오히려 그 요구가 강하다.
- **현장 계측 부재** — "3초 안에 끝낸다"는 설계 목표이지 측정값이 아니다. 실제 소요 시간, 강제 접수 발생률, 재시도율을 기록해 두면 다음 설계의 근거가 된다.

### *Design Decisions.*

| 결정 | 근거 |
|---|---|
| 로그인 없음 | 기기가 공용이다. 계정을 전제할 수 없다 |
| 확인 카드에 이름을 최대 크기로 | 확인 대상은 행위가 아니라 **사람**이다 |
| 완료된 행을 목록에 유지 | 사라지면 본인 확인 경로가 없어져 운영자를 찾게 된다 |
| 성공 후 3초 자동 복귀 | 초기화 조작을 사용자에게 요구하지 않는다 |
| 예외를 같은 저장소에 플래그로 | 현장은 막지 않고, 사후 구분은 가능하게 |
| 폴백 상태를 헤더에 표시 | 조용한 폴백은 은폐다 |
| 폴링과 구독을 함께 | 구독은 조용히 죽고, 죽은 것이 화면에 안 보인다 |
| 삭제는 기본 차단 | 되돌릴 수 없는 조작의 기본값은 잠김이어야 한다 |

### *Term.*

- **키오스크(kiosk)** — 불특정 다수가 순서대로 사용하는 무인 단말. 개인화·학습을 전제할 수 없다
- **점진적 좁힘(progressive filtering)** — 입력이 늘어날수록 후보가 줄어드는 검색 방식. 사용자가 언제 멈출지 스스로 판단하게 한다
- **접두 일치(prefix match)** — 문자열의 앞부분이 일치하는지 보는 검색. 한 글자를 넣을 때마다 결과가 좁혀진다
- **오터치(mis-touch)** — 의도하지 않은 지점을 누르는 것. 대형 터치 화면에서는 상시 발생한다
- **막다른 길(dead end)** — 사용자가 더 진행할 수 없는 상태. 줄이 있는 환경에서는 곧 병목이다
- **폴백(fallback)** — 주 경로가 불가능할 때의 대체 동작. 대체되었다는 사실이 보여야 한다
- **폴링(polling)** — 주기적으로 서버에 다시 물어보는 방식. 구독이 조용히 끊긴 경우의 보험이다
- **미들웨어(middleware)** — 요청이 화면에 도달하기 전에 서버가 가로채는 계층. 클라이언트가 우회할 수 없다
- **`HttpOnly` 쿠키** — 자바스크립트로 읽을 수 없는 쿠키. 스크립트를 통한 탈취를 막는다
- **유일 제약(unique constraint)** — 같은 값이 두 번 들어오는 것을 데이터베이스가 거부하는 규칙. 중복 방지의 최종 판정자
- **`touch-action` / 콜아웃(callout)** — 터치 제스처 처리 방식 지정 / 길게 눌렀을 때 뜨는 복사·공유 메뉴
- **홈 화면에 추가(Add to Home Screen)** — 웹 주소를 앱 아이콘처럼 설치하는 기능. 설치 파일 배포 없이 전체화면 실행이 가능해진다
- **웹 매니페스트 / 서비스워커** — 설치 메타데이터를 담는 파일 / 네트워크 요청을 가로채 오프라인 동작을 만드는 스크립트. **표준 PWA의 두 필수 요건**
